# External Integrations

The platform integrates with several external services to provide its core functionality. Each integration has its own authentication flow, data format, and error handling pattern. This document covers the integration architecture, including payment processing, API integrations with external data sources, push notifications, and social login.

---

## Payment Gateway Integration

The payment gateway handles all payment processing — subscription management, payment method storage, invoice generation, and payment retry flows. No card data ever touches the application servers.

### Architecture Overview

```
Frontend (Secure tokenization library)
    |
    |-- Card data tokenized client-side
    |-- Tokenized PaymentMethod sent to backend
    v
Backend (Payment Gateway API)
    |
    |-- Customers API
    |-- Subscriptions API
    |-- Invoices API
    |-- Webhooks (async events)
    v
Payment Gateway Infrastructure
    |
    |-- Card networks (Visa, MC, Amex)
    |-- SCA authentication (3D Secure)
    |-- Automatic billing
```

### Subscription Lifecycle

```
Free Trial --> Active --> Past Due --> Unpaid --> Canceled
                        |                          |
                        v                          v
                   Retry Payment               End of Period
                        |                          |
                        v                          v
                   Active                      Expired
```

**Free Trial:** Users sign up and get access to all features for a trial period. No payment method required during signup. The trial converts automatically at the end of the period.

**Active:** The subscription is in good standing. Invoices are paid automatically on the billing date using the stored payment method.

**Past Due:** A payment fails (expired card, insufficient funds, SCA required). The subscription enters past_due status. The subscription settings page polls for status changes — checking every 10 seconds for up to 90 seconds. If the payment succeeds during this window, the UI updates automatically.

**Unpaid / Canceled:** If payment cannot be collected after several attempts, the subscription is marked as unpaid. The user loses access to premium features at the end of the current billing period.

### Payment Processing Flow

The payment flow handles Strong Customer Authentication (SCA) requirements:

1. User selects a plan and enters card details
2. Card data is tokenized client-side using the payment gateway's secure components — the server never touches raw card numbers
3. Backend creates a customer record and subscription
4. If SCA is required, the response includes an authentication action requiring client-side confirmation (3D Secure challenge)
5. The frontend handles the authentication iframe transparently
6. On success, the subscription is activated

### Upgrade and Addon Flow

Subscription upgrades (plan changes, addon toggles, ASIN capacity changes) follow the same pattern:

- **Plan upgrade/downgrade**: Changing between plan tiers
- **PPC addon toggle**: Enabling/disabling PPC Automation
- **ASIN capacity changes**: Enterprise users can increase ASIN tracking count
- **Billing cycle changes**: Switching between monthly and yearly billing

Each upgrade may require SCA verification depending on the amount change. The flow handles this by checking for the `requires_action` flag in the response and redirecting to the authentication flow when needed.

### Payment Retry Flow

When a subscription enters past_due status:

1. Users can retry payment with their existing card or enter a new card
2. If SCA is required, the 3D Secure challenge flow runs
3. On success, the subscription returns to active status
4. The polling mechanism on the subscription settings page detects the status change automatically

### Invoice and Receipt System

Invoices are generated by the payment gateway on each billing cycle. The platform provides:
1. **Invoice list** — Sortable, paginated table showing all historical invoices
2. **Invoice receipt** — Formatted receipt page with line items, tax breakdown, and totals
3. **PDF download** — Invoices downloadable as PDF via the gateway's API, fetched as a binary blob and offered for download

### Payment Method Management

Payment methods are stored as tokenized references from the payment gateway:
- Cards are added through secure iframe components — the application never touches raw card numbers
- Users can set any saved card as their default payment method
- The default is used for all subsequent subscription charges

### Key Implementation Detail: PDF Download

Invoice PDFs are fetched as binary data (blob) from the API. A temporary URL is created in the browser, and a programmatic click triggers the download with the correct filename. Using the blob response type is critical — without it, the HTTP client would try to parse the PDF as JSON and fail silently.

## External Data Source API Integration

The primary external data source provides access to marketplace seller data. This is the most data-intensive integration because it syncs inventory, orders, shipments, and financial data across multiple marketplaces.

### Data Sync Architecture

```
Sync Scheduler (scheduled job)
    |
    v
External Data API (REST)
    |
    |-- Rate limited: N requests per second per seller
    |-- Paginated responses
    |-- Exponential backoff on throttling
    v
Background Worker Queue
    |
    |-- Sequential steps (inventory -> products -> sales -> etc.)
    |-- Each step fetches + processes + stores
    v
Database
```

### Rate Limit Handling

External APIs impose strict rate limits. The system handles this with:
1. **Job queueing**: Sync requests are queued and processed sequentially
2. **Exponential backoff**: On throttling responses, the worker waits with exponential delay before retrying
3. **Batch processing**: Where possible, multiple items are fetched in a single API call
4. **Throttle-aware scheduling**: The scheduler knows rate limits for each endpoint and paces requests accordingly

### Authentication Flow

The API uses OAuth 2.0 with a two-step authorization flow:
1. User is redirected to the external service's authorization page
2. User grants permissions and is redirected back with an authorization code
3. Backend exchanges the code for a long-lived refresh token and short-lived access token
4. Refresh tokens are stored encrypted server-side
5. Access tokens are refreshed transparently before API calls

### Separate Authorization for Multiple APIs

Two separate API integrations exist with independent authorization:

- **Selling API**: Access to inventory, orders, shipments, and financial data
- **Advertising API**: Access to campaign and advertising performance data

Users authorize each independently. The authorization status is tracked separately in the frontend state.

## Push Notification Service

The notification service handles push notifications and real-time updates through two complementary channels.

### Dual-Channel Architecture

| Channel | When It Works | Best For |
| ------------------- | ---------------------------------- | -------------------------------- |
| Push notifications | App in background or closed | Time-sensitive alerts |
| Real-time signals | App in foreground | Instant badge count updates |

### Push Notification Delivery

Push notifications are delivered through the service's messaging infrastructure:
- When the app is in the background, the service worker handles incoming push events
- A browser notification is displayed with title, body, and action data
- Clicking the notification navigates to the relevant page
- Service worker checks for existing tabs before opening new ones

### Real-Time Signal Updates

Real-time updates are delivered through a document database subscription:
- Each user has a summary document tracking unread notification count
- The frontend subscribes to changes on this document
- When the document changes (new notification arrives), the badge count updates instantly
- The initial snapshot on subscription is skipped because data is first loaded via REST API

### Graceful Degradation

The notification service requires specific configuration values. If not configured, notification features are silently disabled — the app works perfectly without them, users simply do not get browser notifications.

## OAuth (Social Login)

OAuth provides social login functionality. The flow uses the standard OAuth 2.0 authorization code flow:

1. User clicks "Sign up with Google" (or similar provider)
2. OAuth dialog opens
3. User grants email and profile access
4. Provider returns a credential token
5. Frontend sends the credential to the backend
6. Backend verifies the token with the provider's API
7. If the user exists, they are logged in. If new, an account is created

## Integration Service Layer

All external integrations are abstracted behind service layers:

```
Frontend Components
    |
    |-- Calls service functions (e.g., getCampaigns(), submitPayment())
    v
Service Layer
    |
    |-- Handles auth, request formatting, data transformation
    v
Network Layer
    |
    |-- HTTP client with interceptors
    |-- Token injection, error handling, response parsing
    v
External APIs
```

### Network Layer Configuration

The HTTP client is preconfigured with:
- Base URL from environment variables
- Automatic JSON content type headers
- Timeout values appropriate for the environment
- An interceptor that attaches the auth token to every request
- A response interceptor that handles global error conditions:
  - **401**: Clears tokens, redirects to login
  - **403**: Shows permission error
  - **Network errors**: Shows generic error notification
  - **All other errors**: Passes through to component-level handlers

## Interview Talking Points

**On the payment SCA handling:** "European regulations require 3D Secure authentication for many online payments. When the gateway returns `requires_action`, the frontend triggers a challenge flow that opens an iframe for the user to authenticate with their bank. The entire checkout flow handles this transparently — the user sees the bank's authentication dialog within our page, and the subscription activates on success."

**On the subscription polling:** "When a payment fails, the settings page polls every 10 seconds for up to 90 seconds. If the user retries payment and it succeeds, the UI updates automatically without a manual refresh."

**On the PDF download pattern:** "Invoice PDFs are fetched as binary blobs. We create a temporary download URL using the browser's blob URL API. The `responseType: 'blob'` configuration is critical — without it, the HTTP client would try to parse the PDF as JSON and fail silently."

**On the dual notification channel architecture:** "Push notifications work when the tab is in the background, but they are one-way — the app does not know a notification arrived until the user interacts with it. Real-time document subscriptions give us instant badge count updates when the user is actively using the app. The two channels complement each other."

**On the service layer abstraction:** "Each external integration has a service that wraps the API communication. The frontend never calls external APIs directly. It calls domain functions, and those functions handle authentication, request formatting, and error handling. This makes the UI code cleaner and allows changing integrations without touching components."
